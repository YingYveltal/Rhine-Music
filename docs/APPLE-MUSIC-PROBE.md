# Apple Music 无会员原型验证（Issue #6）

**公开接口路线已能读取现有歌单并控制订阅曲目，尚未接入 Rhine。** Music.app 承担播放，原型是浏览与遥控界面；未使用开发者会员、MusicKit 令牌、凭据读取或私有 API。实际出声仍待用户确认，不把进度推进写成主观听感通过。

本轮实际运行源码 `4c5a3c4a21ff10c0de17ae695a7b8dc4bb07dcdc`，可执行 SHA256 `75b38d8497fa80c4f24e5fb34aee9ea39c0ced3b21d151ed145e3e0dd59bad99`。固定 Bundle ID 为 `com.rhine.music.appleprobe`，macOS 14+，ad-hoc Hardened Runtime 签名及 Apple Events entitlement。后续仅报告改动不重建，不将报告提交冒充运行源码。

## 实测结果

- 公开权限预检明确返回需要同意（-1744），用户正常允许后返回 0。后续重建保留固定身份，本轮预检为 0。初版未经预检时的 -1712 超时保留为历史现象，不能等同于权限拒绝。
- 读取已有歌单，曲目顺序与 Music.app 的可见列表逐项对照一致。所测音乐的 `cloud status` 为 `subscription/kSub`，`kind` 为 Apple Music AAC；不是仅以歌曲名称推断来源。
- 指定订阅单曲后，探针和 Music.app 同时显示该曲目，完整曲长及实际进度持续推进，应用音量非零且未静音。没有采集或导出受保护音频。
- **原型自身调用 `play(playlist)`** 可建立系统共享队列；下一首、暂停保持、定位、恢复、上一首和停止通过。定位尾段再恢复后自动续到后一首；Music.app 已有 AutoMix 开启且未改动，不将它表述为整碟长时/无缝音质验收。
- 正常停止并退出 Music.app 后，探针明确提示未运行，连接返回 -600、播放按钮禁用；重新打开 Music.app 后连接恢复。
- 没有制造空资料库、拒绝/撤销授权或网络故障。实际自然分类有内容，空库不算通过。

## 中间点播的确定限制

`play(track)` 能播放选中的曲目，但会清空系统后续待播队列。实测在已建立歌单队列后直接点播中间曲目，再发 `nextTrack`，命令虽成功但仍播放同一曲；Music.app 待播清单明确为空。该现象在单曲起播和歌单中间点播均观察到。

因此，`play(id)` 与 `Music.nextTrack` 不等价，不能直接套用 Rhine 现有播放器后宣称整个队列闭环已经通过。独立 Music.app 手工建立队列后控制成功的早期对照，与原型自身建立队列成功的后续测试分别记录；后者才是本轮可用闭环。

## 最小接入判断

已可靠验证的是两种明确行为：**整歌单播放由 Music.app 自己维护共享队列；任意曲目可单独点播**。接入时可在现有曲库中显示 Apple 歌单，建立一小段原生桥接，针对 Apple 来源调用这组公开命令并回读实际状态。Apple 控制不走 QQ 下载/rodio 解码；切换来源先停止另一播放器。授权须以最终 Rhine 应用身份重新验收，不能继承探针的许可结论。

现有 `NativeMusicPlayer` 的前后切歌按本地队列调用 `play(id)`，EOF 在 Rust 音频 worker 内完成。桥接器逐曲接管这份队列在工程上可以尝试，但当前公开脚本状态没有与 rodio 同等的确定 EOF 回调。轮询中，自然结束和用户在 Music.app 尾段手动停止都可能表现为停止且位置归零。只凭“接近末尾”自动续歌可能覆盖用户停止，尚不能称为可靠方案。

Rhine 自己的暂停/停止可用命令代次和播放意图取消后续动作；检测到 Music.app 外部换曲或暂停，应放弃队列所有权或同步状态，不能把歌曲强行拉回。但这些措施不能消除外部停止与自然 EOF 的全部歧义。更快轮询、按时间猜测、临时写用户歌单或操控音量跳过中间曲都不是本轮已验证方案。

建议下一步先将已验证桥接能力接入最小界面，并单独解决“从中间点播后继续队列”的语义和验收；不提前扩建通用队列框架，也不把两种播放行为隐瞒为同一种。属性分次读取在切歌瞬间还可能组合出前后两首的短暂混合快照，产品桥接需检查曲目身份一致后再提交状态。
