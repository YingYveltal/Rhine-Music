# 开发与验收入口

开发总控通过现有两个开发对话的主 agent 派工；开发工作不交给 subagent。subagent 仅在有需要时做有明确范围的只读核查或独立复核。每个执行对话只使用分配的 Git worktree，所有命令明确工作目录；已授权的职责与证据要求见根目录 AGENTS.md。

## 任务与恢复

[全部任务](https://github.com/YingYveltal/Rhine-Music/issues)按 `workstream:*`、`status:*` 和优先级标签筛选。Issue 保存需求和依赖，PR 保存交付，Git 提交标识对应源码；标签反映当前阶段，关闭的 Issue 还须在记录中说明是否已交付应用或发布。

两个长期方向分别是播放器与音乐源、渲染与交互。分支按具体 Issue 创建，完成一项后从最新 main 开始下一项，不长期维护两个相互分裂的产品。

恢复时先查看开放的 Issue、PR、分支及工作目录状态，按任务引用读取必要证据。不把旧对话摘要当作当前源码状态，不复制完整开发日志来维持上下文。任务进入开发后，起点提交、执行对话、工作目录与交付 PR 记录在对应 Issue 中；本机路径只在本机派工资料中使用。

## 常规检查

```sh
npm ci
npm --prefix frontend ci
bash scripts/check.sh
```

`Checks / macos-checks` 在 PR 和 main 更新时运行。使用 macOS 15、Node 24.14.0、Rust 1.93.1，检查前端构建、内容和视口约束、音乐与动画契约、既有渲染算法检查，以及两个 Rust crate 的默认测试。依赖由现有锁文件固定。

ignored 测试需要真实音频设备或用户会话，不在 CI 自动运行。真实扫码、钥匙串操作、用户曲库、视觉对比与性能基准由总控协调；开发者不得把 CI 通过写成这些项目已经通过。设备性能测试与重型构建排队执行，以免相互影响。

## 合并

开发对话提交并推送自己的分支，创建关联 Issue 的 PR；未完成验收时保持草稿。总控检查 PR 当前提交与证据对应、最新主线的组合结果和未覆盖范围，然后串行合并。相同 GitHub 登录下的另一个 agent 不算另一个 GitHub 审批账号。

仓库的实际主线保护设置由总控在 Issue #2 中记录。若账号不能启用保护，必须如实保留这一限制，不把协作约定描述为平台已强制执行。正式发布及新的产品取舍按已授权范围交用户决定。

## 来源与历史约束

初始源码来源见 `baseline-source.json`；初始提交为 QQ 源码快照。前端旧文档和 AGENTS.md 中的历史发行信息不能用作向上游仓库推送或公开发布的当前授权。用户最新指令优先，正式发布与本轮工程迁移分开。
